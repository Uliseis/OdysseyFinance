# Decisions

Settled choices. Don't reopen one by drifting from it in code. Add a new entry that supersedes it, and mark the old one.

Format: **decision**, why, and when it's worth revisiting.

---

### D1. Native iOS app, no server
**Decision.** A native SwiftUI app with all logic on the device. No backend and no account system; the iCloud account is the boundary.
**Why.** Single user; bank data shouldn't sit on a server the app has to secure.
**Revisit when.** A second user or a web client is needed.

### D2. SwiftData locally, CloudKit private database via `CKSyncEngine`
**Decision.** SwiftData `@Model` types as the store, synced through a hand-rolled `CKSyncEngine` layer, not `NSPersistentCloudKitContainer`.
**Why.** Explicit control over conflict resolution, deduplication and push timing (see D3, D4).
**Revisit when.** `NSPersistentCloudKitContainer` gains custom conflict policies.

### D3. Conflict policy: last writer wins, except manual categories
**Decision.** Records resolve by `updatedAt`. A transaction whose category was set by hand (`categorySource == .manual`) keeps that category against any non-manual write.
**Why.** A bank re-sync on another device must never undo a choice made by hand.

### D4. Composite uniqueness in code, never `#Unique`
**Decision.** `Transaction(account, externalId)` and `FxRate(date, currency)` are deduplicated in `CoreSync` (`CompositeDedupe` and the pull pipeline). Enforced by `scripts/check-repo.sh`.
**Why.** `#Unique` resolves conflicts by a silent, non-deterministic upsert that rewrites the row's `id`. That breaks the `CKRecord.recordName == id` invariant and the deterministic winner across devices.
**Revisit when.** SwiftData lets the caller choose which row survives.

### D5. Deletes through SwiftData delete rules
**Decision.** Bare `ctx.delete(model)`. Cascades and nullifies come from `@Relationship(deleteRule:)`, including the recursive ones (`Transaction.routedFromTx`, `Category.parent`). `CascadeTests` guards all four delete shapes.
**Why.** The iOS 18 bug that needed explicit cascade helpers is fixed on iOS 26.
**Revisit when.** `CascadeTests` fails on a new SDK: restore explicit helpers.

### D6. Money is `Decimal`, EUR first, ECB rates
**Decision.** Amounts are `Decimal` in storage and logic (matching the original `numeric(p,s)` columns). Every transaction keeps its original currency, its EUR amount and the ECB rate used. Charts convert to `Double` only to plot.

### D7. Enable Banking on the device
**Decision.** Enable Banking (PSD2) is called straight from the app. RS256 JWTs are signed on the device with the application key, which is stored in the iCloud Keychain. The bank-consent redirect is an `https` URL on the app's associated domain, served as static files from `Vercel/`.
**Why.** There is no server to hold a key (D1), and a single-user app never ships the key inside a distributed binary.
**Revisit when.** The app is distributed to other people.

### D8. Spaces, shared expenses and investments
**Decision.** Any number of spaces, with cross-space transfer invariants. Shared expenses are kept. Investments are tracked per account as valuation snapshots plus a cost-basis anchor, with live values from Trading 212 and CoinGecko. ~~There is no per-instrument holdings model.~~ Superseded by D16 for funds imported from a broker's order export.
**Revisit when.** Per-position reporting (lots, dividends per instrument) is needed.

### D9. Category source is never null
**Decision.** `categorySource` is a non-optional `CategorySource` (`bank`, `rule`, `manual`). Rows imported without one were backfilled to `.bank`.

### D10. The web app is a frozen spec
**Decision.** `Spec/` is a read-only snapshot of the original Next.js app, kept as the porting reference. It was migrated once (`Tools/`); the web app is decommissioned. Enforced for PRs by `scripts/check-repo.sh`.

### D11. Generated, not committed: Xcode project and icon PNGs
**Decision.** `OdysseyFinance.xcodeproj` is generated from `project.yml` by XcodeGen and ignored. The app icon PNGs are generated by `design/app-icon/make_icon.py` and committed; edit the script, never the PNGs.

### D12. Public repository with no personal data (2026-10-18)
**Decision.** The repository is public. No real balances, transactions, merchants, people, account identifiers or record counts appear in code, fixtures, commit messages or PR descriptions. Keys, statements and stores never enter git.
**Why.** Pushed content is archived by third parties within minutes and can't be recalled. The history was rewritten once to remove such data.

### D13. Claude bridge through the app's iCloud Drive container (2026-11-15)
**Decision.** Claude works on the data from the Mac through a local MCP server (`Tools/OdysseyMCP`) that only exchanges files with the app's iCloud Drive container (`iCloud.com.uliseis.odysseyfinance`, under `bridge/`). The app writes `snapshot.json`: the full history of every model with secrets stripped (session ids, tokens, connection metadata, raw bank payloads, sync metadata). The server writes batched commands to `inbox/`. The app previews a batch, shows it for review, applies it through CoreLogic on the main context after Face ID, and writes the outcome to `results/`. Per-type auto-apply exists only for non-destructive changes and is off until switched on in Settings. Bank keys, JWT signing and SCA stay on the phone: Claude can only ask for a sync or a reconnect prompt. Shared types live in `CoreBridge`, which the server links, so it runs the same CoreLogic on an in-memory copy of the snapshot.
**Why.** No server (D1) and a single CloudKit writer (D2): a second CloudKit client brings conflicts that are hard to reason about. CoreLogic saves inside every mutation, so a preview can only run on an isolated in-memory copy, never on a context over the real store. Full history because a balance is an opening or anchor plus every row since.
**Revisit when.** A Mac app becomes a CloudKit client, or the snapshot outgrows one file.

### D14. Auto-applied Claude batches must be signed by a paired Mac (2026-11-15)
**Decision.** Extends D13. The MCP server signs every batch with a P256 key kept in the Mac's login Keychain and publishes the public key to `bridge/keys/`. The phone trusts a key only after the user compares its fingerprint and confirms with Face ID. Auto-apply (per-type switches, off by default, Face ID to turn one on) requires a verified signature; unsigned or unknown-key batches always open the review sheet marked unverified, and a batch whose signature doesn't match its paired key is rejected.
**Why.** The inbox is a folder any program on the Mac, and any device on the iCloud account, can write to. Review plus Face ID guards a batch; auto-apply skips that, so it needs proof of origin. Signing doesn't stop a program on the paired Mac that runs the server binary itself; the switches stay off by default and every auto-applied batch can be undone.
**Revisit when.** The server runs somewhere other than the user's own Mac, or a batch type outside the safe set is considered for auto-apply.

### D15. A Mac helper app claims the bridge container (2026-11-16)
**Decision.** Extends D13. `Tools/OdysseyBridgeHelper` is a minimal signed Mac app whose entitlements name the app's iCloud container. It stays installed in `~/Applications`, and opening it once registers the container on the Mac. It never touches CloudKit's database, and the MCP server still reads the folder by path.
**Why.** macOS syncs an app's private iCloud Drive container only while an app that names it is installed on the Mac. Without one, the iCloud daemon marks the container "app not installed", stops syncing it and drops the local copies. The bridge worked at first only because the Mac had created the folder itself. iPhone builds registered on the Mac don't count.
**Revisit when.** The MCP server ships as an app bundle that can claim the container itself, or a Mac app becomes a CloudKit client (D13).

### D16. Fund positions from imported broker orders (2026-11-16)
**Decision.** Supersedes D8's "There is no per-instrument holdings model." An investment account can carry fund trades imported from the broker's order export: one buy or sell of a fund, by ISIN, with its units and EUR amount. Units, first-in-first-out cost and realised gains per fund derive from the trades and are never typed. Cash at the broker is an anchor plus transfers since, minus buys, plus sells. Market value comes from fund prices by ISIN; the price source is decided in its own entry. Pension plans and robo portfolios without an export stay typed valuations (D8).
**Why.** A typed snapshot aged silently and showed a loss for months. Per-fund realised and unrealised results need the buy and sell prices, which only the orders carry.
**Revisit when.** A broker offers an API for positions, or a second broker's export needs importing.

### D17. Fund prices from EODHD (2026-11-16)
**Decision.** Fund NAVs come from EODHD's free plan, addressed by ISIN on its fund exchange (`<ISIN>.EUFUND`), with the API key in the Keychain. Each fund's name and currency are looked up once; its price is fetched at most once a day, and the app stops at a daily request cap below the plan's limit. Prices are cached on the device and never synced. The FT is not used in the app: history older than a year is a one-off backfill done outside the app and recorded as dated valuations. Prices are a day behind, and a one-day-old NAV is acceptable for net worth.
**Why.** There is no free official API for European fund NAVs. EODHD covers the funds held, with more decimals than the FT's pages, and scraping pages from the app breaks silently.
**Amended (2026-11-17).** A value is dated by the prices it uses, not by when the refresh ran, and the days missed since the last valuation are filled from the same request: each fund's one daily request returns a window of NAVs reaching back a week before that valuation (within the plan's year), and every weekday up to the newest held fund's price day is valued with each fund at its latest price on or before that day. The newest day can mix in a day-old NAV for a fund that publishes later.
**Revisit when.** The plan's limit is reached, or EODHD stops covering a held fund.

### D18. API keys readable after first unlock (2026-11-17)
**Decision.** The Enable Banking key and application ID, and the Trading 212 and EODHD keys, are stored readable after the first unlock since boot (`kSecAttrAccessibleAfterFirstUnlock` for the iCloud-synced items, the `ThisDeviceOnly` variant for any that don't sync), no longer only while the iPhone is unlocked. Keys saved before are re-protected when the app next comes to the foreground with the phone unlocked; only the protection attribute changes. There is no biometric access control on the items.
**Why.** The background bank sync, the daily price refresh and the *Sync & Refresh* Shortcuts action run while the phone sits locked, and couldn't read the keys. The keys stay encrypted until the first unlock after boot and are never readable by other apps. The bank key only grants read (AIS) access. Face ID still guards the app lock and Claude batches.
**Revisit when.** A key gains write or payment power, or the device threat model changes.
